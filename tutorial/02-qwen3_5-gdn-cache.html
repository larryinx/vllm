Qwen3.5 推理：前向计算与 Gated DeltaNet 的状态缓存

Qwen3.5 是「线性注意力 + 全注意力」的混合模型。本讲以 Qwen3.5-9B（bf16，单卡，FlashAttention 后端）为例，看一层层前向怎么走，以及 vLLM 如何把两种完全不同的缓存放进同一个显存池。

要点

  • 结构：每 4 层为一组，前 3 层是 Gated DeltaNet（GDN） 线性注意力，第 4 层是带输出门的 全注意力。9B 共 32 层，其中 24 层 GDN、8 层全注意力。
  • 全注意力层和第 1 讲一样使用分页 KV cache，存的是 RoPE 后的 K，大小随上下文线性增长。
  • GDN 层每个请求只保存两份固定大小的状态：conv_state（最近 3 个 token 的 q/k/v 输入，供短卷积使用）和 ssm_state（每个 value head 一个 128 × 128 的矩阵 S）。它们与上下文长度无关，每层约 2 MiB。
  • prefill 用分块并行算法（块长 64）从初始状态算到末状态并写回；decode 每个 token 用递推 kernel 原地更新状态。
  • 两种缓存共用一个块池。为了让一个「块」既能装下 GDN 一层的完整状态，又能装下注意力一层的若干 token，vLLM 把注意力的 block_size 从 16 调到 528。

整体结构

层的类型由 HF 配置里的 layer_types 决定。缺省时按 full_attention_interval = 4 生成：第 i 层当 (i + 1) 能被 4 整除时是全注意力，否则是线性注意力（vllm/transformers_utils/configs/qwen3_5.py 第 88–96 行）。Qwen3.5-9B 的实际配置正是如此：

GDN 线性注意力（24 层）全注意力（8 层：3, 7, …, 31）

vLLM 里 Qwen3.5 的实现大量复用 Qwen3-Next：Qwen3_5DecoderLayer 继承 Qwen3NextDecoderLayer，按层类型创建 QwenGatedDeltaNetAttention 或 Qwen3NextAttention。每层的前向就是标准的 pre-norm 残差结构，只是「注意力」这一步分两种：

vllm/model_executor/models/qwen3_next.py · Qwen3NextDecoderLayer.forward（第 549 行起，节选）
hidden_states, residual = self.input_layernorm(hidden_states, residual)

if self.layer_type == "linear_attention":
    hidden_states = self.linear_attn(hidden_states=hidden_states)   # 注意：不需要 positions
elif self.layer_type == "full_attention":
    hidden_states = self.self_attn(hidden_states=hidden_states, positions=positions)

hidden_states, residual = self.post_attention_layernorm(hidden_states, residual)

GDN 层不接收 positions：它没有位置编码，token 的先后顺序由卷积和递推本身体现。只有全注意力层用 RoPE。

和 Qwen3-Next 相比，Qwen3.5 的差异主要有三点：checkpoint 里 GDN 的投影是分开存的（in_proj_qkv、in_proj_z、in_proj_b、in_proj_a），加载时融合成 in_proj_qkvz 和 in_proj_ba（qwen3_5.py 第 220–226 行）；融合后的权重是 [q, k, v, z] 顺序，不需要 Qwen3-Next 那种交错布局的重排（gqa_interleaved_layout=False）；Qwen3.5 自带视觉编码器，全注意力层用 M-RoPE。

门控全注意力层

Qwen3NextAttention 在普通 GQA 上加了三样东西：q 投影同时输出一个同样大小的门 gate；q、k 先过 RMSNorm（QK-Norm）；注意力输出乘以 sigmoid(gate) 后再进 o_proj。9B 的参数是 16 个 q head、4 个 KV head、head_dim 256，RoPE 只转前 64 维（partial_rotary_factor = 0.25），且是交错 M-RoPE（mrope_section = [11, 11, 10]，θ 基数 107）。

vllm/model_executor/models/qwen3_next.py · Qwen3NextAttention.forward（第 449–461 行）
def forward(self, positions, hidden_states):
    qkv, _ = self.qkv_proj(hidden_states)
    q, k, v, gate = self._project_qkv_gate(qkv, positions)  # split + QK-Norm + RoPE
    attn_output = self.attn(q, k, v)                         # 写 KV cache + 注意力
    if gate is not None:
        attn_output = attn_output * torch.sigmoid(gate)
    output, _ = self.o_proj(attn_output)
    return output

在 CUDA 上，split、QK-Norm、RoPE 和拆出 gate 由一个 Triton kernel fused_qk_rmsnorm_rope_gate 一次完成。之后 self.attn 就是第 1 讲的 Attention：k′、v 按 slot_mapping 写进分页 cache。每个 token 每层占 4 个 KV head × (256 + 256) × 2 B = 4 KiB，8 层合计 32 KiB。

GDN 层的前向

GDN 层的实现是 vllm/model_executor/layers/mamba/gdn/qwen_gdn_linear_attn.py 里的 QwenGatedDeltaNetAttention。9B 的 GDN 有 16 个 q/k head 和 32 个 v head，head 维度都是 128；每个 q/k head 服务 2 个 v head（线性注意力里的 GQA）。一次前向分三段：

一个 GDN 层的数据流（Qwen3.5-9B，单卡）。两个带颜色的方框就是这一层要缓存的全部状态。

  1. ① 投影：in_proj_qkvz 输出 q（2048）、k（2048）、v（4096）、z（4096）；in_proj_ba 输出每个 v head 一个 b 和一个 a（各 32）。
  2. ② 核心：q/k/v 拼在一起（conv_dim = 8192）做深度可分离的短卷积，卷积核长 4，接 SiLU；然后 q、k 做 L2 归一化；由 a、b 算出衰减 g 和写入强度 β；最后跑门控 delta 规则，更新状态并得到输出 o。这一段被包成自定义算子 torch.ops.vllm.qwen_gdn_attention_core。
  3. ③ 输出：RMSNormGated 对每个 v head 的 o 做 RMSNorm，再乘以 SiLU(z)，最后 out_proj 投回 hidden_size。
vllm/model_executor/layers/mamba/gdn/qwen_gdn_linear_attn.py · forward_cuda（第 895 行起，节选）
mixed_qkvz, _ = self.in_proj_qkvz(hidden_states)
ba, _ = self.in_proj_ba(hidden_states)
# Qwen3.5: weights are already in [q, k, v, z] and [b, a] order
mixed_qkv, z = mixed_qkvz.split([qkv_size, z_size], dim=-1)
b, a = self.split_ba(ba)

core_attn_out = torch.zeros((num_tokens, self.num_v_heads // self.tp_size, self.head_v_dim), ...)
torch.ops.vllm.qwen_gdn_attention_core(
    mixed_qkv, b.contiguous(), a.contiguous(), core_attn_out,
    layer_name=_encode_layer_name(self.prefix),
)
return self._output_projection(core_attn_out, z)   # RMSNormGated + out_proj

为什么要包成自定义算子？核心部分要根据当前 batch 的元数据（多少个 prefill、多少个 decode、哪些是投机解码）在 Python 里分支，还要原地改写状态缓存，这些都没法被 torch.compile 追踪成静态图。所以这个算子被列为 CUDA graph 的切分点（和普通注意力一样），投影、归一化这些前后部分照常编译和捕获，核心部分夹在图的片段之间执行。在支持的配置上（bf16、head 维度 128、SM80 及以上），默认还会走一个把 RMSNormGated 也融进去的变体 qwen_gdn_attention_core_fused_norm_packed，逻辑相同。

门控 delta 规则：状态 S 在做什么

对每个 v head，状态 S 是一个 dv × dk = 128 × 128 的矩阵，可以把它看成一个「键 → 值」的联想记忆：给一个 k，S·k 就是它记住的值。每来一个 token t：

αt = exp(gt)，gt = −exp(A_log) · softplus(at + dt_bias)，βt = σ(bt)
St = αt·St−1 + βt·(vt − αt·St−1kt)·kt⊤
ot = St · qt / √dk

三个动作依次是：先按 α 整体衰减（遗忘，α ∈ (0, 1)）；再用衰减后的 S 读出 k 当前对应的值，与真实的 v 比较得到误差；最后按 β 的比例把误差写回 k 的方向。和普通线性注意力「只加不改」相比，delta 规则会覆盖同一个键上的旧值，所以在固定大小的状态里记得更准。vLLM 的 CPU 测试里有一段逐 token 的参考实现，最直观：

tests/kernels/mamba/cpu/test_cpu_gdn_ops.py（第 167–178 行，参考实现）
for token_idx in range(seq_len):
    ...
    g_t = g_seq[:, :, token_idx].exp().unsqueeze(-1).unsqueeze(-1)   # α_t
    beta_t = beta_seq[:, :, token_idx].unsqueeze(-1)
    state = state * g_t                                   # 衰减
    kv_mem = (state * k_t.unsqueeze(-2)).sum(dim=-1)      # 读：S·k
    delta = (v_t - kv_mem) * beta_t                       # 误差 × β
    state = state + delta.unsqueeze(-1) * k_t.unsqueeze(-2)   # 写：+ δ·kᵀ
    out_seq[:, :, token_idx] = (state * q_t.unsqueeze(-2)).sum(dim=-1)

这里的 A_log 和 dt_bias 是每个 v head 一个的可学习参数（A_log 用 fp32 存）。GPU 上 g、β 的计算和 q、k 的 L2 归一化被融进 Triton kernel（prefill 在 fused_gdn_prefill_post_conv.py，decode 在递推 kernel 内部）。

prefill 与 decode：同一份状态，两种算法

这一步和注意力完全不同：GDN 层不需要读整段历史，只需要「上一步留下的状态」。所以 vLLM 的元数据构建器 GDNAttentionMetadataBuilder（vllm/v1/attention/backends/gdn_attn.py）给每个请求算出三样东西：它的状态存在哪个槽（state_indices）、是否已有状态（has_initial_state = 已计算 token 数 > 0）、以及它在本 batch 里是 decode 还是 prefill。batch 会被重排成「decode 在前、prefill 在后」（reorder_batch_threshold = 1），GDN 层据此分两路：

decode（每个请求 1 个新 token）prefill / chunked prefill 的一段
短卷积causal_conv1d_update：用 conv_state 里的 3 个历史输入加新输入算出 1 个输出，窗口原地左移一格causal_conv1d_fn：已有状态时从 conv_state 读 3 个历史输入，否则补零；算完把这段的最后 3 个输入写回
状态更新逐 token 递推 kernel（fused_recurrent_gated_delta_rule_packed_decode 等），在 ssm_state 上原地更新 Schunk_gated_delta_rule：以 64 个 token 为一块，块内用矩阵乘并行，块间传递状态；初始状态取自 ssm_state，算完把末状态写回
每步开销与上下文长度无关：每层把 S 读一遍、写一遍与本段长度成正比

prefill 路径的状态读写写得非常直白：

vllm/model_executor/layers/mamba/gdn/qwen_gdn_linear_attn.py · _forward_core（第 1495–1523 行，节选）
prefill_state_indices = attn_metadata.prefill_state_indices
prefill_has_initial_state = attn_metadata.prefill_has_initial_state
initial_state = ssm_state[prefill_state_indices]
initial_state[~prefill_has_initial_state, ...] = 0        # 新请求从零状态开始
(core_attn_out_non_spec, last_recurrent_state) = self.chunk_gated_delta_rule(
    q=query_non_spec, k=key_non_spec, v=value_non_spec, g=g_non_spec, beta=beta_non_spec,
    initial_state=initial_state, output_final_state=True,
    cu_seqlens=attn_metadata.prefill_query_start_loc, ...
)
# Init cache
ssm_state[prefill_state_indices] = last_recurrent_state.to(ssm_state.dtype)

这也解释了 chunked prefill 为什么能工作：一个 8K 的 prompt 被切成几段分几步算，第二段开始 has_initial_state 为真，直接从上一段写回的状态接着算，结果和一次算完相同。prefill 的 chunk kernel 在 H100 上默认用 FlashInfer 实现，其他情况用 Triton（FLA）实现。只有纯 decode 的 batch 才能用完整 CUDA graph（AttentionCGSupport.UNIFORM_BATCH）。

状态的形状与大小

每个 GDN 层向 vLLM 报告两份状态的形状，公式在 MambaStateShapeCalculator.gated_delta_net_state_shape：

vllm/model_executor/layers/mamba/mamba_utils.py（第 278–300 行）
conv_dim = head_k_dim * num_k_heads * 2 + head_v_dim * num_v_heads
conv_state_shape = cls._orient_conv_shape(
    divide(conv_dim, tp_world_size), conv_kernel_size - 1 + num_spec,
)
temporal_state_shape = (
    divide(num_v_heads, tp_world_size), head_v_dim, head_k_dim,
)
return conv_state_shape, temporal_state_shape

代入 9B 的配置（单卡、不开投机解码）：

48 KiBconv_state：[3, 8192] × bf16。卷积核长 4，只需记住前 3 个输入
2 MiBssm_state：[32, 128, 128] × fp32。32 个 v head 各一个 S
2,146,304 B每个请求每个 GDN 层的状态合计，约 2.05 MiB
49 MiB每个请求 24 个 GDN 层合计，与上下文长度无关

两个 dtype 是分开控制的：conv_state 跟随 --mamba-cache-dtype（默认即模型 dtype，bf16）；ssm_state 跟随 --mamba-ssm-cache-dtype。后者设为 auto 时，vLLM 会读取 HF 配置中的 mamba_ssm_dtype，Qwen3.5 的官方配置写的是 float32（vllm/model_executor/models/config.py 第 819 行起）。递推的数值误差会一步步累积，所以 S 用 fp32 存。

张量并行时，conv_dim 和 v head 数都按 TP 切分，每张卡只存自己那部分 head 的状态。注意 ssm_state 的最后两维是 [d_v, d_k]，也就是 S 的行对应 v、列对应 k。

一层 GDN 的状态是 2,146,304 B，恰好等于一层全注意力 524 个 token 的 KV cache（524 × 4 KiB）。把这件事画出来：下面比较 Qwen3.5-9B 与一个假想的「32 层全是全注意力」的同尺寸模型，每个请求需要多少缓存。

两种缓存，同一个显存池

vLLM v1 只有一个块池（BlockPool），所有层共用一套块号。可是两种层对「一块」的需求完全不同：注意力层一块存 block_size 个 token，GDN 层一块要装下一整份状态。vLLM 的做法是让两者的页大小（每层每块的字节数）相等。

第一步：放大注意力的 block_size

GDN 层用 MambaSpec 描述，页大小就是所有状态的字节数之和。启动时 Platform._align_hybrid_block_size 找出满足「注意力页 ≥ GDN 页」且是 kernel 对齐单位（FlashAttention 为 16）整数倍的最小 block_size：

vllm/platforms/interface.py · _align_hybrid_block_size（第 835 行起，节选）
attn_block_size = kernel_block_alignment_size * cdiv(
    mamba_page_size,
    kernel_block_alignment_size * attn_page_size_1_token,
)
if cache_config.block_size < attn_block_size:
    cache_config.block_size = attn_block_size
...
# Pad mamba page size to exactly match attention page size
attn_page_size = cache_config.block_size * attn_page_size_1_token
cache_config.mamba_page_size_padded = attn_page_size

代入 9B：16 × ⌈2,146,304 ÷ (16 × 4096)⌉ = 16 × 33 = 528。启动日志里会看到 Setting attention block size to 528 tokens。此时注意力页是 528 × 4 KiB = 2,162,688 B，GDN 页被补齐到同样大小（多出 16 KiB，约 0.8%）。换成 Qwen3.5-35B-A3B（只有 2 个 KV head，每 token 每层 2 KiB），同样的公式得到 1056。开 TP=2 时两边都减半，9B 仍是 528。

GDN 层拿到自己那一页后，MambaBase.bind_kv_cache 把它切成两段视图：开头是 conv_state，紧接着是 ssm_state，剩下的补齐部分不用（vllm/model_executor/layers/mamba/abstract.py 第 28 行）。

第二步：按层分组，组与组共享同一块显存

KV cache 管理器把同类型的层分组，并要求每组层数相同。9B 有 8 层全注意力、24 层 GDN，于是组大小取 8：1 个注意力组，加上 3 个 GDN 组（第 i 组取 GDN 层列表的 [i::3]）。结果非常整齐：第 j 个「层槽」由第 4j、4j+1、4j+2 层（GDN）和第 4j+3 层（注意力）共用。

显存上，每个层槽是一段连续的页数组，所有组都从同一个起点映射过来（kv_cache_utils.py 中的注释 “Groups alias from byte 0”）。这之所以安全，是因为一个块号同一时刻只属于一个组：块 5 如果分给了请求 A 的注意力组，那 8 个层槽里的第 5 页就都是 A 的 K/V；如果分给了某个 GDN 组，就都是那 8 个 GDN 层的状态。一个块号因此对应 8 × 2,162,688 B = 16.5 MiB。

前缀缓存与投机解码

前缀缓存：只需要边界处的一份状态

vLLM 默认开启前缀缓存，此时 Qwen3.5 的 GDN 层使用 mamba_cache_mode = "align"（Qwen3.5 不支持 "all"，在 qwen3_5.py 第 332 行直接报错）。align 模式的思路是：

  • GDN 组的 block_size 也设为 528，块表按位置编号：第 p 块用来存「恰好处理完 (p + 1) × 528 个 token 时的状态」。
  • 调度器在 prefill 时把每段切到 528 的整数倍处结束（Scheduler._mamba_block_aligned_split），保证状态恰好落在边界上。
  • 请求跨过一个边界时，分配新块作为运行中的状态块，前向之前由 preprocess_mamba 把上一步的状态拷贝过去；旧块保留下来，成为可被命中的前缀缓存。块表中更早的位置填空块，每个请求同时持有的真实 GDN 块只有 2 个左右。
  • 命中时，注意力层需要前缀的全部 KV 块，GDN 层却只需要命中边界处的那一个状态块（MambaManager.find_longest_cache_hit 从右往左找最后一个已缓存的状态块）。

元数据构建器通过 mamba_get_block_table_tensor 从块表中取出运行中的那一列作为状态槽，GDN kernel 看到的依然只是「每个请求一个 state index」。

投机解码（MTP）

Qwen3.5 自带一层 MTP 草稿头，可以用投机解码。设每步草稿 token 数为 n：

  • conv_state 的长度从 3 变为 3 + n，多留出草稿 token 的输入；
  • 每个请求额外分配 n 个状态块，递推 kernel 在处理第 i 个草稿 token 后把状态写到第 i 个槽；
  • 下一步从第「接受数 − 1」个槽读初始状态（fused_sigmoid_gating.py 第 104–112 行），被拒绝的草稿 token 对应的状态直接丢弃，不需要回滚。

conv_state 变长会改变 GDN 页大小，所以开投机解码后算出的注意力 block_size 也可能不同。
