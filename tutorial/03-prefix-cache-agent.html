前缀缓存：Agent 每次带着工具结果回来，整段上下文会重新 prefill 吗？

本讲沿着一个 agent 循环，从 HTTP 请求一路追到 KV 块池，讲清前缀缓存（Automatic Prefix Caching）的键、查找、写入和驱逐，以及哪些情况命中、哪些不命中。文中标为「实测」的命中数字不是估算：它们来自在 CPU 上直接运行 vLLM 自己的 KVCacheManager 得到的结果。

短答

关掉缓存

会，整段重新 prefill。vLLM 的 OpenAI 接口不保存会话。每次工具结果回来，客户端都要把 system、工具定义、全部历史和新的工具结果整个发过来，引擎把它当成一个全新的请求，从第 0 个 token 开始全部重算。唯一的例外是纯注意力模型配置了 KV connector（如 --kv-offloading-size 的 CPU 卸载）；Qwen3.5 这类混合模型没有例外。

打开缓存

前缀缓存默认就是开的。新请求先在块池里找「从第 0 个 token 起、逐块完全相同」的最长前缀，命中的部分直接复用 KV，只 prefill 剩下的。实测一个 4 轮 agent 循环（block 16 的纯注意力配置），需要计算的 prompt token 从 2,619 个降到 843 个。

命中条件

token id 逐个相同、以整块为单位、从开头连续；这些块还没被驱逐；cache_salt 和 LoRA 一致；请求落在同一个引擎实例上。任何一处不同，从那一块开始往后全部不命中。

Qwen3.5

命中以 528 个 token 为单位。默认配置只保证命中到上一轮 prompt 的末尾（向下取整到 528 的倍数），上一轮模型生成的回复会被重算。

每一轮都是一个新请求

先把 agent 循环在服务端长什么样说清楚。以 /v1/chat/completions 为例，一次工具调用往返是这样的：

  1. 客户端发送 messages = [system, user] 和 tools。服务端渲染聊天模板、分词，交给引擎；模型生成一个工具调用，请求结束。
  2. 客户端（agent 框架）在本地执行工具，拿到结果。这段时间服务端什么都不知道。
  3. 客户端发送 messages = [system, user, assistant(tool_calls), tool(结果)]，也就是上一轮的全部内容再加上新的工具结果。服务端重新渲染整个模板、重新分词，生成一个新的引擎请求。

服务端这一侧没有「会话」：OnlineRenderer 每次都从 request.messages 从头渲染；对 HF 分词器，模板先渲染成文本，再重新分词；引擎收到的 EngineCoreRequest 携带完整的 prompt_token_ids，请求 ID 还会被追加随机后缀，所以永远是一个新的 Request。请求里的 session_id 字段（或 X-Session-ID 头）只用于给 KV 事件打标签，不保存任何状态，也不参与缓存的键。

还要区分两件事。同一个请求内部，decode 不会重新 prefill：调度器每一步把 num_computed_tokens 往前推，新 token 只算自己。跨请求时，唯一能记住上一轮 KV 的，就是 KV 块池里的前缀缓存。所以你问的问题，答案完全取决于前缀缓存。

关掉前缀缓存时，代码里发生了什么

前缀缓存默认开启：CacheConfig.enable_prefix_caching 默认为 True，命令行参数默认为 None，再由模型是否支持来决定（解码器模型和混合模型都支持）。用 --no-enable-prefix-caching 可以关掉。关掉后，沿着一个新请求看三处代码：

命中为 0，num_computed_tokens 就是 0，num_new_tokens 等于整个 prompt 的长度（超过 max_num_batched_tokens 时分成几步做 chunked prefill，但每个 token 都要算一遍）。单元测试 test_basic_prefix_caching_disabled 直接验证了这一点：关缓存后，一个与刚结束的请求共享前缀的新请求，命中数是 0，需要重新分配全部 4 个块。

代价随轮数快速增长：第 k 轮要重算前 k−1 轮积累的全部上下文，总 prefill 量约等于各轮 prompt 长度之和，大致随轮数平方增长。上面的 4 轮例子里是 2,619 对 843，3.1 倍；轮数越多、工具结果越长，差距越大。请求被抢占时也一样：抢占会释放块并把 num_computed_tokens 归零，关缓存时恢复就意味着把 prompt 和已生成的输出全部重算。

例外：配置了 KV connector 时，即使关掉前缀缓存，引擎仍会计算块哈希，调度器仍会问 connector「你那里有多少」。对纯注意力模型，OffloadingConnector（--kv-offloading-size）确实能把上一轮的 prompt 从 CPU 加载回来；它默认只卸载 prompt（offload_prompt_only=True），上一轮的回复仍要重算。对 Qwen3.5 这样的混合模型，关缓存会把 GDN 的缓存模式强制设为 none，此时 OffloadingConnector 在启动时就会断言失败，SimpleCPUOffloadConnector 会自行关闭，没有任何 connector 能恢复 GDN 状态，每一轮都是完整重算。

缓存的键：块哈希链

vLLM 把每个请求的 token 序列切成固定大小的块（纯注意力模型默认 16 个 token 一块），每个满块算一个哈希。关键在于哈希的输入包含上一块的哈希：

vllm/v1/core/kv_cache_utils.py · hash_block_tokens（第 674–680 行）
if not parent_block_hash:
    parent_block_hash = NONE_HASH

curr_block_token_ids_tuple = tuple(curr_block_token_ids)
return BlockHash(
    hash_function((parent_block_hash, curr_block_token_ids_tuple, extra_keys))
)

除了 token id，哈希还会混入一些额外键，让 token 相同但 KV 不同的块彼此区分：

vllm/v1/core/kv_cache_utils.py · generate_block_hash_extra_keys（第 628–647 行）

额外键加在哪些块上对 agent 的意义
cache_salt只加在第 0 块；通过哈希链传给后面所有块同一会话的每一轮必须带同一个 salt（或都不带），否则从第 0 块就不命中。用来隔离租户。
LoRA 名称每一块中途换 adapter，整段不命中。
多模态内容哈希 + 块内偏移与图片等占位 token 重叠的块同一张图片再次出现在历史里，内容哈希相同，可以命中。
prompt embeds 的 SHA-256对应的块直接传 embedding 时，用它区分内容。

几个容易误会的细节：

  • 哈希链的起点 NONE_HASH：默认算法 sha256（以及 sha256_cbor）用固定种子 "vllm-none-hash"，所以不同进程、重启前后、不同 DP 引擎对相同内容算出相同哈希；选 xxhash 时种子是每个进程随机的（除非设了 PYTHONHASHSEED），跨实例不一致。算法由 --prefix-caching-hash-algo 选择。
  • 只有满块才有哈希。最后不满一块的那几个 token 没有键，不可能被别的请求命中。
  • 生成的 token 也会被哈希。每次 append_output_token_ids 之后都会调用 update_block_hashes，新凑满的块立刻得到哈希。所以上一轮的回复（比如工具调用的 JSON）可以被下一轮复用，前提是下一轮重新渲染、重新分词后得到完全相同的 token id。
  • session_id 不参与哈希。不同会话发同样的 prompt，照样共享缓存。
vllm/v1/request.py（第 272–288 行，节选）：输出 token 追加后立即补算新满块的哈希
def append_output_token_ids(self, token_ids: int | list[int]) -> None:

查找：从第 0 块开始，遇到第一个不同就停

调度器只对 num_computed_tokens == 0 的等待请求做一次查找，也就是新请求或被抢占后重新排队的请求；正在运行的请求不会再去找新的命中。查找入口是 KVCacheManager.get_computed_blocks：

vllm/v1/core/kv_cache_manager.py（第 282–300 行，节选）

# to obtain logits. Thus, set max_cache_hit_length to prompt_length - 1.
...

    self.coordinator.find_longest_cache_hit(
        request.block_hashes, max_cache_hit_length

)

对全注意力层，find_longest_cache_hit 就是一个从左到右的循环：逐块查哈希表，查不到就停（哈希是链式的，后面一定也查不到），命中长度 = 命中块数 × block_size：

vllm/v1/core/single_type_kv_cache_manager.py · FullAttentionManager（第 794–802 行）
# Phase 1: longest run of cached full blocks from the start. A missing
# block implies every later block misses too (chained hashes).
for block_hash in itertools.islice(full_block_hashes, max_length // block_size):
    cached_block = block_pool.get_cached_block(block_hash, kv_cache_group_ids)
    if not cached_block:
        break
    for computed, cached in zip(computed_blocks, cached_block):
        computed.append(cached)
hit_length = len(computed_blocks[0]) * block_size

于是命中长度有一个简单的公式。设新 prompt 长 L 个 token，前 d 个 token 与缓存中的某个序列完全相同，块大小为 B：

命中 = ⌊ min(d, L − 1) ÷ B ⌋ × B

两个「向下取整」都会让你损失一些 token：第一个分歧点所在的那一块，以及「最后一个 token 必须重算以产生 logits」导致的那一块。拖动下面的滑块看看：

命中之后，调度器把 num_computed_tokens 设为命中长度，只调度剩下的 num_tokens − num_computed_tokens 个 token；model runner 给这些 token 的位置从 num_computed_tokens 开始编号，所以命中的 token 不会再进模型，它们的 KV 只通过块表被注意力读取。这也和第 1 讲呼应：cache 里存的是 RoPE 之后的 K，同一前缀出现在同样的位置，K 完全一样，直接可用。

有两个请求级开关会让查找直接跳过：设置了 prompt_logprobs（需要每个 prompt token 的 logprob，必须全部重算），以及 Chat Completions 的 echo=True（它会把 prompt_logprobs 默认设成 top_logprobs，即 0）。这类请求不读缓存，但仍然会把自己的块写进缓存。

写入、共享与驱逐：块池里发生了什么

块池（BlockPool）启动时就创建了所有块。每块有一个引用计数 ref_cnt，空闲块串在一个双向链表 free_block_queue 里；另有一张哈希表 cached_block_hash_to_block，键是「块哈希 + KV cache 组号」。

写入：每一步调度时就登记

新请求命中后，allocate_slots 先 touch 命中的块：引用计数加 1，若它在空闲队列里就把它摘出来，防止被驱逐。然后从空闲队列队头取新块给未命中的部分，最后把已经填满的块登记进哈希表：

vllm/v1/core/kv_cache_manager.py · allocate_slots（第 597–606 行）
# NOTE(woosuk): We want to commit (cache) up to num_local_computed_tokens
# + num_external_computed_tokens + num_new_tokens, but must exclude
# "non-committable" tokens (e.g., draft tokens that could be rejected).
# Therefore, we cap the number at `request.num_tokens`, ensuring only
# "finalized" tokens are cached.
num_tokens_to_cache = min(
    total_computed_tokens + num_new_tokens,
    request.num_tokens,
)
self.coordinator.cache_blocks(request, num_tokens_to_cache)

这段代码在 prefill 和每一步 decode 时都会执行，所以：

  • 块在调度时就进了哈希表，不必等请求结束。几个同时运行、共享 system 与工具定义的子 agent，可以立刻共用同一批物理块（ref_cnt 变成 2、3…）。对全注意力层这是安全的：同一次前向里，每一层都是先写 KV 再算注意力。
  • decode 填满的块同样会被登记，这就是上一轮回复能被下一轮命中的原因。
  • 最后一个采样出来的 token 从没被送进模型，它所在的块不会被这一轮登记。

释放：请求结束后 KV 还在

vllm/v1/core/block_pool.py · free_blocks（第 793–805 行）
block.ref_cnt -= 1
if block.ref_cnt == 0 and not block.is_null:
    if block.block_hash is None or not self.enable_caching:
        # LIFO reuse of non-cached blocks for better GPU locality.
        blocks_to_evict_first.append(block)
    else:
        # FIFO reuse of cached blocks for LRU eviction behavior.
        blocks_to_evict_last.append(block)

# Blocks to reuse first are prepended to the front of the free queue.
self.free_block_queue.prepend_n(blocks_to_evict_first)
# Blocks to reuse last are appended to the end of the free queue.
self.free_block_queue.append_n(blocks_to_evict_last)

请求结束时，块按逆序释放（最后一块先释放）。有哈希的块被放到空闲队列队尾，并且保留哈希：它们既是「空闲」的，又仍然可以被命中。没有哈希的块（不满一块的尾巴，或关缓存时的所有块）被放到队头，最先被重用。

驱逐是惰性的：只有当 get_new_blocks 从队头取走一个有哈希的块分给别人时，才把它从哈希表删掉。没有过期时间，只有显存压力。这对 agent 很重要：工具执行期间（可能几秒到几分钟）服务端在服务别的请求，如果流量大、显存紧，你的上一轮可能被挤掉。模拟程序的「显存压力」场景把块池缩到 70 个块，每轮之间插入一个无关的大请求：第 2 轮命中从 368 降到 208，第 4 轮从 864 降到 0。

还有两点：监控里的 KV cache 使用率把「空闲但仍缓存着」的块算作空闲，使用率低不代表缓存被清空；vLLM 不去重相同内容的块，两个并发请求如果都在各自计算同一段新前缀，会各存一份。

官方设计文档 docs/design/prefix_caching.md 说「释放的块按逆序加到队尾」，那是早期行为；现在没有哈希的块会被放到队头。本讲以代码为准。

Agent 场景：哪些命中，哪些不命中

把上面的规则落到 agent 循环里。默认前缀缓存开启，按纯注意力模型（如 Llama 类）讨论；混合模型见下一节。

场景结果原因
同一会话下一轮，工具结果追加在末尾命中前缀不变；上一轮 prompt 和回复中已凑满的块都能复用（实测第 2 轮 368 / 510）。
多个并行子 agent 共享 system 和工具定义命中块在调度时即被登记，同时运行的请求共用物理块。
请求被抢占后恢复通常命中抢占释放的块带着哈希回到队尾，恢复时重新查找，没被驱逐的部分能命中。
历史里再次出现同一张图片命中图片的内容哈希作为额外键，相同图片得到相同的键。
原样重发同一个请求大部分命中最后一个 token 必须重算，可能因此损失一整块。
system prompt 里有时间、随机 ID几乎全不命中变化出现在第 0 块，整条链都变。实测：第 5 个 token 每轮变化，4 轮命中全为 0；同样的变化放在第 299 个 token，每轮只能命中前 288 个。gpt-oss 的 Harmony 格式会注入当天日期（可用 VLLM_SYSTEM_START_DATE 固定）；vLLM 文档也提到 Claude Code 曾在 system prompt 里注入逐请求的哈希。
改了工具列表或工具描述几乎全不命中多数模板把工具定义渲染在 prompt 开头附近（system 段或第一条用户消息里）。
客户端改写了历史从改写处起不命中实测：第 3 轮删掉第 1 轮回复的前 20 个 token，命中从 544 降到 336（改动发生在第 337 个 token，向下取整到 336）。

「上一轮回复能不能被复用」取决于模板

引擎只认 token id，而下一轮的 prompt 是服务端重新渲染文本、重新分词得到的，并不是把上一轮生成的 token id 原样拼上去。研究时我们用 Qwen3.5 的真实分词器和 vLLM 的真实消息处理代码做了逐 token 对比（没有 GPU，生成的 token 用文本的标准分词代替）：

  • 同一个工具循环内（中间没有新的用户提问）：只要客户端把 vLLM 返回的 reasoning 字段原样回传，下一轮 prompt 能逐 token 复现上一轮的 prompt 和生成内容，包括思考、工具调用 XML 和结尾的 <|im_end|>。
  • 新的用户提问到来时：Qwen3.5 的模板只给「最后一个真实用户提问之后」的 assistant 消息保留 <think>，更早的会被去掉。于是上一个工具循环的第一条 assistant 消息起就和缓存不一致，整个上一轮循环（包括工具结果）都要重算；更早的 system、工具定义和历史仍然命中。
  • 容易出错的地方：客户端没回传 reasoning（第一个生成 token 就对不上）；思考内容为空；工具参数是布尔值（生成的 true 被渲染回 True）；模型生成了紧凑 JSON 而模板的 tojson 加了空格。

Qwen3.5（混合模型）的特殊规则

第 2 讲讲过：Qwen3.5-9B 的全注意力块和 GDN 状态块都是 528 个 token，一个物理块要么放注意力 KV，要么放一份 GDN 状态。前缀缓存对它有三条额外规则：

  1. 命中以 528 为单位。所有 KV cache 组的块大小都是 528，哈希粒度（hash_block_size）也是 528，子块级的「部分命中」不生效。
  2. 命中长度取各组的最小值。全注意力组需要前缀的全部块；GDN 组只需要命中边界处的那一份状态（它已经概括了之前的所有 token）。两者不一致时，以短的为准。
  3. GDN 状态不是每块都有。开前缀缓存时 GDN 使用 align 模式：状态只在某个调度步恰好结束在 528 的倍数处时才存在。再加上默认的 prefix_cache_retention_interval = 0，只保留两类检查点：prompt 末尾向下取整处（⌊(P − 1) / 528⌋ × 528）和共享前缀的分叉点。decode 过程中经过的 528 边界不保留。

合起来，对 agent 循环的影响是：下一轮最多命中到上一轮 prompt 的末尾（向下取整到 528）。上一轮 prompt 末尾不足 528 的零头、上一轮的整个回复、新的工具结果都要重新 prefill。vLLM 自带的端到端测试 test_hybrid_prefix_cache_hit_rate.py（用 Qwen3.5-0.8B 跑多轮对话）断言的正是这个下限。

还有一个边界情况：如果上一轮 prompt 的长度恰好是 528 的倍数，并且一次 prefill 就算完了，那么 P − 528 处的状态从没被算出来，下一轮会退回到更早的检查点，最坏命中 0；再下一轮会通过分叉点检查点自动恢复。

可以调的两个参数：

  • --prefix-cache-retention-interval：设为 None（保留全部检查点）或 528 的正整数倍 K，decode 时经过的边界也会被保留，下一轮就能命中到上一轮回复里面。代价是缓存的状态块变多：每个检查点位置 3 个 GDN 组各占一块，约 49.5 MiB。
  • --prefix-match-unit u（u 整除 528 且小于 528）：在 prompt 末尾登记更细的「部分命中」入口，命中能精确到 u 个 token。代价是 prefill 多出一两个调度步（要在那些位置停下来存状态），命中时还要复制一次状态块。它不会让命中进入上一轮回复。

并行子 agent 在混合模型上也有区别：第一个与已有请求只共享 system 前缀的兄弟请求命中为 0（GDN 没有那个位置的状态），但它会在分叉点停下来存一份状态；之后的兄弟请求就能命中到分叉点（向下取整到 528）。如果先用一个「只有共享前缀」的请求预热，所有兄弟都能直接命中。

怎么观察命中

  • 每个请求：启动时加 --enable-prompt-tokens-details，响应的 usage.prompt_tokens_details 里会有 cached_tokens（命中的 token 数，含 connector 的外部命中）和 created_cache_tokens。Anthropic 兼容接口 /v1/messages 对应 cache_read_input_tokens 和 cache_creation_input_tokens。agent 循环里可以看着 cached_tokens 每轮增长。
  • 全局指标：Prometheus 计数器 vllm:prefix_cache_queries 和 vllm:prefix_cache_hits（单位是 token；被抢占后重新进入的请求不计入；connector 的命中另计在 vllm:external_prefix_cache_*）。日志里定期打印 Prefix cache hit rate。因为最后一个 token 总要重算，原样重发也不会显示 100%。
  • 压测：benchmarks/multi_turn/benchmark_serving_multi_turn.py 会把模型的真实回答作为历史回放多轮对话，报告 TTFT、TPOT 等，可以对比开关缓存的差别。
  • 清空缓存：POST /reset_prefix_cache（或 LLM.reset_prefix_cache()），只有在没有块被占用时才会成功。

写 agent 时怎样让缓存多命中

  1. 稳定的放前面，变化的放后面。system prompt 和工具定义不要包含时间、随机 ID、计数器；需要的话放到最后一条消息里。
  2. 历史只追加，不改写。不要压缩、截断或重排旧消息；确实要压缩上下文时，接受那一轮会从改动处重算。
  3. 原样回传 vLLM 返回的字段，尤其是 reasoning 和工具调用的参数，避免客户端自己重新格式化。
  4. 同一会话用同一个 cache_salt，也不要中途切换 LoRA。
  5. agent 请求里不要开 prompt_logprobs 或 chat 的 echo。
  6. 多实例部署时做会话粘性路由，让同一会话的每一轮落到同一个引擎。
  7. 显存紧张时考虑 --kv-offloading-size 把冷块卸载到 CPU，扩大缓存容量（纯注意力模型；混合模型需在开前缀缓存的前提下使用）。
  8. Qwen3.5 等混合模型：如果上一轮回复很长、又希望复用，可以试 --prefix-cache-retention-interval，用显存换命中。
