全注意力 + RoPE 模型：KV cache 怎么存，K 是旋转前还是旋转后？

以 Llama 这类标准 MHA / GQA 模型为例，沿着一次前向计算，从 rotary_emb 一直追到把 K、V 写进显存的 CUDA kernel。

旋转后POST-RoPE K
  • 模型在调用 self.attn(q, k, v) 之前就对 q、k 施加了 RoPE，所以 Attention 层拿到、并写进 cache 的是 k′ = RoPE(k, pos)。v 不做位置编码，原样写入。
  • 每个 token 的 K 只旋转一次：在它被算出来的那一步，用它自己的绝对位置旋转，然后写入 cache。之后的每一步 decode 都直接读，不会再旋转。
  • cache 是分页的（PagedAttention）：每层一个逻辑张量 [B, H, N, C]，即「块 × KV head × 块内 token × 内容」，其中内容维 C 把同一个 token、同一个 head 的 K 和 V 拼在一起。token 写到哪一格由 slot_mapping 决定。

模型代码里的顺序

先看模型定义。vLLM 里几乎所有使用 RoPE 的全注意力模型都遵循同一个模式，Llama 是最典型的（代码里的中文注释是教程加的，下同）：

vllm/model_executor/models/llama.py · LlamaAttention.forward（第 224–234 行，节选）
def forward(self, positions, hidden_states):
    qkv, _ = self.qkv_proj(hidden_states)
    q, k, v = qkv.split([self.q_size, self.kv_size, self.kv_size], dim=-1)
    q, k = self.rotary_emb(positions, q, k)   # RoPE 发生在这里
    attn_output = self.attn(q, k, v)           # 传进去的已经是旋转后的 q、k
    output, _ = self.o_proj(attn_output)
    return output

这里的 positions 是每个 token 在自己序列里的绝对位置（第 0、1、2… 个 token）。rotary_emb 在 CUDA 上走的是原地（in-place）kernel ops.rotary_embedding，直接改写 q、k 的显存（见 rotary_embedding/base.py 第 242 行的注释）。所以从 self.attn 往后，已经不存在「未旋转的 K」了。

一次前向中单层的数据流。q′、k′ 表示已旋转。cache 里只存 k′ 和 v，q′ 用完即丢。

Attention 层内部：先写 cache，再算注意力

Attention.forward 把 k′、v reshape 成 [num_tokens, num_kv_heads, head_size]，然后分两步：

vllm/model_executor/layers/attention/attention.py · Attention.forward（第 488 行起，节选）
key = key.view(-1, self.num_kv_heads, self.head_size)
value = value.view(-1, self.num_kv_heads, self.head_size_v)
...
kv_cache_dummy_dep = torch.ops.vllm.unified_kv_cache_update(key, value, encoded)
torch.ops.vllm.unified_attention_with_output(
    query, key, value, output, encoded,
    kv_cache_dummy_dep=kv_cache_dummy_dep,   # 保证 torch.compile 下「先写后读」
)

unified_kv_cache_update 会调用当前后端的 impl.do_kv_cache_update。以 FlashAttention 后端为例：

vllm/v1/attention/backends/flash_attn.py · FlashAttentionImpl.do_kv_cache_update（第 1510 行起，节选）
# (B, H, N, 2*D) -> ((B, N, H, D), (B, N, H, D))
key_cache, value_cache = kv_cache.transpose(1, 2).split(self.head_size, dim=-1)
reshape_and_cache_flash(
    key, value, key_cache, value_cache, slot_mapping,
    self.kv_cache_dtype, layer._k_scale, layer._v_scale,
)

reshape_and_cache_flash 是一个纯粹的「按地址搬运」kernel：它根据 slot_mapping 算出每个 token 在 cache 里的位置，把 k′、v 拷贝过去。如果 KV cache 是 fp8，它会顺便乘上 k_scale / v_scale 做量化。它不做任何旋转。

写完之后，forward 再调用 flash_attn_varlen_func，传入的是 cache（k=key_cache, v=value_cache）和 block_table，而不是刚算出来的 k、v。也就是说，在 v1 的 FlashAttention 后端里，prefill 和 decode 通常都从分页 cache 里读 K/V。kernel 拿到的 q′ 和 cache 中的 k′ 都已旋转，直接做点积就是带 RoPE 的注意力分数。

还有一些后端的 forward_includes_kv_cache_update = True，会在 forward 内部自己完成写入，但写进去的内容相同，都是 k′ 和 v。

KV cache 的内存布局

每个注意力层的 cache 规格由 AttentionSpec 描述：block_size（每块多少 token，默认 16，个别后端会调大）、num_kv_heads、head_size、head_size_v 和 dtype。其中决定「每格多大」的是：

vllm/v1/kv_cache_interface.py · AttentionSpec.state_content_size_bytes（第 513 行）
@property
def state_content_size_bytes(self) -> int:
    """Bytes per (head slot, stored state) cell of the page."""
    if self.state_content_bytes is not None:
        return self.state_content_bytes
    return (self.head_size + self.head_size_v) * get_dtype_size(self.dtype)

也就是说，一个「格子」对应 一个 token × 一个 KV head，里面先放 K（head_size 个数），紧接着放 V（head_size_v 个数）。

整个 cache 的逻辑形状是 5 维 [L, B, H, N, C]：层、块、KV head、块内 token、内容（字节）。物理上按什么顺序排由 KVCacheLayout（vllm/v1/kv_cache_layout.py）决定。FlashAttention 后端没有声明偏好，于是用默认的 LBNHC（即过去常说的 NHD 布局）：每层独立一段显存，块内按「token → head → K‖V」连续排列。每层拿到的是一个 4 维视图 [B, H, N, C]，写入和读取前各做一次 transpose(1, 2).split(head_size)，得到两个 [B, N, H, D] 的 strided 视图 key_cache 和 value_cache。

算一笔账：Llama-3-8B（bf16，block_size = 16，单卡）

4 KiB每 token 每层：8 个 KV head × (128 + 128) × 2 B
64 KiB每块每层（一页）：16 token × 4 KiB
128 KiB每 token 全模型：32 层 × 4 KiB
1 GiB一条 8192 token 的序列占用的 KV cache

用张量并行（TP）时，每张卡只存自己那一份 KV head（TP=2 时每卡 4 个），上面的数字相应减半。

slot_mapping：每个 token 写到哪一格

调度器给每个请求分配若干物理块，记在 block_table 里（请求的第 i 个逻辑块 → 第几号物理块）。每一步前向前，worker 用 token 的位置算出它的 slot：

vllm/v1/worker/block_table.py · ComputeSlotMappingKernel（第 475–476 行）
slot_offsets = local_block_offsets % block_size
slot_ids = block_numbers * block_size + slot_offsets

CUDA kernel 再把 slot 拆回「物理块号 + 块内偏移」：

csrc/libtorch_stable/cache_kernels.cu · reshape_and_cache_flash_kernel（第 326 行起，节选）
const int64_t slot_idx = slot_mapping[token_idx];
if (slot_idx < 0) { return; }                  // padding 出来的 token 不写
const int64_t block_idx = slot_idx / block_size;
const int64_t block_offset = slot_idx % block_size;
cache_t* key_dst =
    key_cache + block_idx * block_stride + block_offset * page_stride;
// 之后逐 head 拷贝；fp8 cache 时乘以 k_scale / v_scale

下面用一个缩小版的例子把这些连起来：block_size = 4，2 个 KV head，显存里一共 12 个物理块（只画一层）。一个请求已有 10 个 token，block_table = [7, 2, 9]。拖动滑块或点击任意有数据的格子，看这个 token 的 k′、v 落在哪里。点「decode 一步」模拟生成一个新 token：只有新 token 的一格被写入，已有的格子不变；当前块写满时，会从空闲块里再分配一块。

block_table[7, 2, 9]
token 位置 p5
逻辑块 = p // 41
块内偏移 = p % 41
物理块 = block_table[1]2
slot = 物理块 × 4 + 偏移9
K 部分（存 k′，已按 p 旋转） V 部分 其他请求占用 空闲

每个块内一行是一个 token 槽位，每行两组小方块分别是 head 0 和 head 1，每组左 K 右 V。真实配置里 block_size 通常是 16，head 数和块数也多得多。

为什么存旋转后的 K

RoPE 把向量按维度两两分组，每组看作一个二维平面，位置 m 的向量在第 i 个平面上旋转角度 m·θi（θi = base−2i/d，Llama 2 的 base 是 10000，Llama 3 是 500000）。设 Rm 为旋转矩阵，因为旋转矩阵正交且可交换：

⟨Rmq, Rnk⟩ = q⊤Rm⊤Rnk = q⊤Rn−mk

注意力分数只取决于相对距离 n − m。关键在于左边这个形式：k 的旋转只依赖 k 自己的位置 n，与之后哪个 query 来读它无关。一个 token 的位置一旦确定就不会改变，所以在写入时旋转一次，之后所有 query 都能直接用，结果和每次现算完全一样。

0.000分数 ⟨q′, k′⟩，相对距离 m − n = 4

虚线是旋转前的 q、k，实线是旋转后的 q′、k′（示意：单个频率，θ = 0.4 rad）。只拖动 m 时 k′ 不动，因为 key 的旋转只由它自己的位置 n 决定；m 和 n 一起平移时分数不变。因果注意力下 n ≤ m，所以 n 不会超过 m。

反过来，如果 cache 存的是未旋转的 K，会是什么样？

存旋转后的 K（vLLM 的做法）存旋转前的 K
每个 K 旋转几次写入时 1 次每一步 decode 都要把整段历史 K 再转一遍，额外开销随序列长度线性增长
注意力 kernel直接使用 FlashAttention / FlashInfer 等标准 kernel需要在 kernel 内读出 K 后按位置旋转，要定制 kernel
前缀缓存同一前缀出现在同一位置时可复用理论上同一段文本放在不同位置也能复用
改动 token 的位置必须重算（或先做逆旋转）只需改 position

对推理引擎来说，前两行是每一步都要付出的代价，后两行只在少数场景里有用，所以 vLLM 和主流推理框架都选择存旋转后的 K。

这个设计带来的影响

  • 前缀缓存可以直接复用。块哈希由「父块哈希 + 本块 token ids + 额外键（LoRA、多模态等）」算出（kv_cache_utils.py 的 hash_block_tokens）。父块哈希形成一条链，隐含了「这个块从第几个 token 开始」，所以一旦命中，这些 token 的位置必然相同，缓存里的 k′ 也完全一致。反过来，同一段文字出现在不同偏移处就无法命中。
  • 已缓存 token 的位置不能随意平移。像 StreamingLLM 那种丢掉中间 token、把后面 token 的位置往前挪的做法，需要对 k′ 先逆旋转再按新位置旋转。vLLM 的 cache 里没有未旋转的 K，要改位置只能重新计算这些 token。
  • fp8 KV cache 量化的是 k′。reshape_and_cache_flash 在写入时用 k_scale 把 k′ 转成 fp8，量化误差作用在旋转后的值上。
  • RoPE 和写 cache 可以融合成一个 kernel。torch.compile 的 RopeKVCacheFusionPass（开关 fuse_rope_kvcache）把 rotary_embedding 和 unified_kv_cache_update 合并，由后端的 do_rope_and_kv_cache_update 一次完成；Qwen3 这类带 QK-Norm 的模型还有 QK-Norm + RoPE + 写 cache 三合一的版本。目前只在开启 ROCm AITER 的后端上生效。融合只省掉一次显存读写，写进去的仍然是 k′。

变体与特例

部分旋转（partial rotary）

GPT-NeoX、Phi-2、StableLM 等模型的 rotary_dim 小于 head_size，只有前 rotary_dim 维被旋转，其余维度保持原样。cache 里的 K 仍然是「RoPE 处理之后」的整个向量，只不过其中一部分维度没有被转。

M-RoPE（Qwen2-VL / Qwen2.5-VL 等多模态模型）

positions 变成形状 [3, num_tokens] 的（时间、高、宽）三维位置，不同频率段用不同的位置分量。它同样在 self.attn 之前施加，cache 里存的依然是旋转后的 K。

MLA（DeepSeek-V2 / V3）：解耦 RoPE

MLA 不是「全 KV」存储，但正好可以对照。它的 cache 每个 token 只存一行：压缩后的潜向量 kv_c_normed（kv_lora_rank = 512 维，不带位置信息）拼上 单独的 RoPE 部分 k_pe（64 维），一共 576 维，所有 head 共享。

vllm/model_executor/layers/mla.py（第 227–230 行）
if self.rotary_emb is not None:
    q[..., self.qk_nope_head_dim :], k_pe = self.rotary_emb(
        positions, q[..., self.qk_nope_head_dim :], k_pe
    )

写入时 concat_and_cache_mla 把 kv_c_normed 和已旋转的 k_pe 拼在一起存进 [num_blocks, block_size, 576]。MLA 之所以把 RoPE 单独拆出来，是因为潜向量要和 up-projection 矩阵做「矩阵吸收」，只有不带位置信息才能吸收。结论不变：凡是带 RoPE 的那部分 K，vLLM 都存旋转后的值。
